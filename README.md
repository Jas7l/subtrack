# SubTrack

Корпоративная система учёта подписок на ПО: реестр подписок, выдача лицензий,
согласование заявок (сотрудник → начальник отдела → админ), напоминания о
платежах и окончании, аналитика расходов и рекомендации по экономии.
Полное описание — в [task.md](task.md).

Этот репозиторий — серверная часть: REST API на Go (gorilla/mux, pgx, slog),
PostgreSQL.

## Запуск локально

1. Создать базу в PostgreSQL (по умолчанию используется пользователь `postgres`):

   ```sql
   CREATE DATABASE subtrack;
   ```

2. Применить миграции **по порядку номеров**, каждую `up.sql`. Удобнее всего
   выполнить файлы по одному из GoLand (Database → открыть файл → Run) или
   DataGrip. Через `psql`:

   ```sh
   for f in migrations/*/up.sql; do psql -h localhost -U postgres -d subtrack -v ON_ERROR_STOP=1 -f "$f"; done
   ```

   `down.sql` откатывает соответствующую миграцию; откатывать в обратном порядке.

   | Миграция | Что создаёт |
   |---|---|
   | 0001_schema | схему `subtrack` |
   | 0002_users_departments | `departments`, `users` |
   | 0003_currencies | `currencies` (курсы к рублю, RUB = 1) |
   | 0004_subscriptions | `subscriptions`, `subscription_assignments` |
   | 0005_requests | `requests` (заявки и их статусы) |
   | 0006_transactions | `transactions` (платежи) |
   | 0007_notifications_audit | `notifications`, `notification_log`, `audit_log` |
   | 0008_department_heads_and_case | один начальник — максимум один отдел; регистронезависимость для кириллицы (`pg_c_utf8`) |
   | 0009_subscriptions_case | регистронезависимый поиск по названию, вендору и категории подписки (`pg_c_utf8`) |
   | 0010_notification_settings | `notification_settings` (одна строка: за сколько дней предупреждать) |

3. Настроить подключение и запустить:

   ```sh
   cp .env.example .env   # поправить значения при необходимости
   make run               # или: go run ./cmd/server
   ```

   Сервер сам читает `.env` из рабочей директории (другой файл можно указать
   через `ENV_FILE`). Переменные, уже заданные в окружении или в run
   configuration GoLand, имеют приоритет над файлом.

4. Проверка: `curl localhost:8080/healthz` → `{"status":"ok",...}`.

5. Документация API: **http://localhost:8080/swagger/** (Swagger UI).
   Войти: `POST /auth/login` → скопировать `token` → кнопка **Authorize** →
   `Bearer <token>`.

## Аутентификация

Вход по email и паролю, дальше каждый запрос несёт JWT в заголовке
`Authorization: Bearer <token>`.

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| POST | `/api/v1/auth/login` | все | `{"email","password"}` → `{"token","token_type","expires_at","user"}` |
| GET | `/api/v1/auth/me` | с токеном | текущий пользователь |
| POST | `/api/v1/auth/password` | с токеном | `{"current_password","new_password"}` → 204 |

- Токен подписан HS256 ключом `JWT_SECRET` (обязателен, ≥ 32 байт) и живёт
  `JWT_TTL` (по умолчанию 12h). В токене только id пользователя: роль и
  флаг активности перечитываются из БД на каждом запросе, поэтому блокировка
  или смена роли действует сразу, а не после истечения токена.
- Пароли хранятся как bcrypt-хэш; длина пароля 8–72 байта.
- Неизвестный email и неверный пароль дают одинаковый ответ 401 — по API
  нельзя узнать, какие email существуют. Заблокированный пользователь с верным
  паролем получает 403.
- Пользователей создаёт только админ, поэтому **первый админ** создаётся при
  старте сервера из `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD`,
  если в БД ещё нет ни одного активного админа. Когда админ есть, эти
  переменные ни на что не влияют. После первого входа смените пароль через
  `/auth/password`.

```sh
TOKEN=$(curl -s localhost:8080/api/v1/auth/login \
  -d '{"email":"admin@company.ru","password":"change-me-now"}' | jq -r .token)
curl -s localhost:8080/api/v1/auth/me -H "Authorization: Bearer $TOKEN"
```

## Пользователи и отделы

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| GET | `/api/v1/users` | админ, начальник | список; фильтры `department_id`, `role`, `active`, `q`; начальник видит только свой отдел |
| GET | `/api/v1/users/{id}` | все | админ — любого, начальник — своего отдела, сотрудник — только себя |
| POST | `/api/v1/users` | админ | создать: `full_name`, `email`, `password`, `role`, `department_id?` |
| PATCH | `/api/v1/users/{id}` | админ | изменить `full_name`, `email`, `role`, `department_id`, `is_active` |
| PUT | `/api/v1/users/{id}/password` | админ | сбросить пароль |
| GET | `/api/v1/departments` | все | админ — все (фильтр `q`), остальные — только свой отдел |
| GET | `/api/v1/departments/{id}` | все | админ — любой, остальные — только свой |
| POST | `/api/v1/departments` | админ | создать: `name`, `head_id?` |
| PATCH | `/api/v1/departments/{id}` | админ | переименовать / сменить начальника |
| DELETE | `/api/v1/departments/{id}` | админ | удалить пустой отдел |

Правила:

- Пользователи не удаляются: `"is_active": false` блокирует (токены перестают
  работать сразу), `true` — разблокирует.
- Чужой пользователь или отдел вне зоны видимости отвечает 404, а не 403 —
  по API нельзя узнать, существует ли он.
- Админ не может заблокировать себя или снять с себя роль админа (409) — так
  в системе всегда остаётся хотя бы один активный админ.
- Начальником отдела может быть только **активный** пользователь с ролью
  `manager`, и только одного отдела (уникальный индекс, 409). При назначении
  он автоматически переводится в этот отдел; прежний начальник остаётся в
  отделе обычным менеджером.
- Если начальника заблокировали, понизили или перевели в другой отдел, отдел
  остаётся без начальника (`head_id = null`) — в той же транзакции.
- В PATCH `"department_id": null` / `"head_id": null` означает «очистить»,
  а отсутствие ключа — «не менять».
- Удалить можно только пустой отдел: без активных пользователей и без
  подписок (409 с количеством). Заблокированные пользователи отвязываются.
- Email и название отдела уникальны без учёта регистра, в том числе для
  кириллицы.

## Подписки и лицензии

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| GET | `/api/v1/subscriptions` | все | список; фильтры `department_id`, `category`, `status`, `type`, `end_from`, `end_to`, `q` |
| GET | `/api/v1/subscriptions/{id}` | все | одна подписка, если она в зоне видимости |
| POST | `/api/v1/subscriptions` | админ | создать |
| PATCH | `/api/v1/subscriptions/{id}` | админ | изменить, в том числе отменить (`"status": "cancelled"`) |
| DELETE | `/api/v1/subscriptions/{id}` | админ | мягкое удаление |
| GET | `/api/v1/assignments` | все | лицензии; фильтры `subscription_id`, `user_id`, `status` |
| GET | `/api/v1/assignments/{id}` | все | одна лицензия, если она в зоне видимости |
| POST | `/api/v1/assignments` | админ, начальник | выдать: `{"subscription_id","user_id"}` |
| POST | `/api/v1/assignments/{id}/revoke` | все | отозвать (или отказаться от своей) |

Правила:

- Видимость. Админ видит всё. Начальник — подписки своего отдела и лицензии
  на них, плюс свои собственные лицензии. Сотрудник — только подписки, на
  которые у него есть активная лицензия, и свои лицензии. Остальное — 404.
- Типы: `individual` — всегда 1 место (сервер ставит сам), `group` — нужно
  указать `seats_total`, `enterprise` — без лимита (`seats_total` не
  передаётся, в ответе `null`). В ответе есть `seats_used` и `seats_free`.
- `seats_used` меняется только выдачей и отзывом лицензий, в той же
  транзакции. Выдать больше лицензий, чем мест, нельзя (409); уменьшить
  `seats_total` ниже `seats_used` тоже нельзя (409) — сначала отзовите
  лишние лицензии.
- Выдача. Админ выдаёт лицензию любой подписки любому активному
  пользователю. Начальник — только подписки своего отдела и только людям
  своего отдела. Лицензию отменённой или истёкшей подписки выдать нельзя
  (409), повторно тому же человеку — тоже (409).
- Отзыв. Отозвать может админ, начальник отдела-владельца подписки и сам
  владелец лицензии. Отозванная лицензия остаётся в истории; потом человеку
  можно выдать новую.
- Отмена (`"status": "cancelled"`) и удаление подписки отзывают все её
  лицензии в той же транзакции. Удалённая подписка не показывается, но её
  история лицензий и платежей остаётся.
- Блокировка пользователя отзывает все его лицензии.
- Статус вручную можно поставить только `active` или `cancelled`;
  `expiring_soon` и `expired` будет ставить шедулер.
- Стоимость (`cost`) принимается числом или строкой, в ответе всегда строка
  с двумя знаками (`"15000.00"`) — деньги не проходят через float. Валюта —
  код из таблицы `currencies`. Даты — `YYYY-MM-DD`.
- В PATCH `null` очищает `end_date`, `next_payment_date`, `department_id`.
- `next_payment_date` дальше двигает шедулер (см. «Платежи»). Ставьте
  ближайшую будущую дату: на каждую дату в прошлом шедулер создаст платёж
  `pending`. Прошлые оплаты вносятся вручную через `POST /transactions`.
  Смена `type` без `seats_total` сбрасывает места под новый тип.

```sh
curl -s localhost:8080/api/v1/subscriptions -H "Authorization: Bearer $TOKEN" -d '{
  "name": "Jira", "vendor": "Atlassian", "category": "Разработка", "type": "group",
  "cost": "15000.00", "currency": "RUB", "billing_period": "month",
  "start_date": "2026-01-01", "end_date": "2026-12-31", "department_id": 1, "seats_total": 20}'
curl -s localhost:8080/api/v1/assignments -H "Authorization: Bearer $TOKEN" \
  -d '{"subscription_id": 1, "user_id": 7}'
```

## Заявки

```
pending_manager ──reject──▶ rejected_by_manager
      │ approve (начальник отдела)
      ▼
pending_admin ────reject──▶ rejected_by_admin
      │ approve (админ: подписка + лицензия)
      ▼
   approved

pending_manager / pending_admin ──заявитель отменил──▶ cancelled
```

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| GET | `/api/v1/requests` | все | список; фильтры `status`, `requester_id`, `department_id` |
| GET | `/api/v1/requests/{id}` | все | одна заявка, если она в зоне видимости |
| POST | `/api/v1/requests` | сотрудник, начальник | подать: `name`, `justification`, `vendor?`, `estimated_cost?`, `currency?` |
| POST | `/api/v1/requests/{id}/approve` | начальник, админ | одобрить |
| POST | `/api/v1/requests/{id}/reject` | начальник, админ | отклонить: `{"comment"}` (обязателен) |
| POST | `/api/v1/requests/{id}/cancel` | заявитель | отменить, пока заявка не решена |

Правила:

- Заявка сотрудника идёт начальнику его отдела (`head_id`). Если начальника
  нет или у сотрудника нет отдела — сразу админу. Заявка начальника всегда
  идёт сразу админу. Админ сам заявки не подаёт — он создаёт подписки.
- Первый шаг решает только текущий начальник отдела заявки; другой менеджер
  того же отдела видит заявку, но решать не может (403). Если начальника
  сняли, пока заявка ждала, решение принимает админ.
- Видимость: админ — все; начальник — заявки своего отдела и свои
  (входящие: `?status=pending_manager`); сотрудник — свои.
- Отклонение требует комментарий (400). Одобрение — нет.
- Одобряя, админ выбирает подписку: существующую
  (`{"subscription_id": 12}`) или новую (`{"subscription": {...}}` — поля
  как у `POST /subscriptions`; `name`, `vendor` и `department_id` по
  умолчанию берутся из заявки, `"department_id": null` — общая на
  компанию). Заявителю выдаётся лицензия.
- Создание подписки, выдача лицензии и смена статуса — одна транзакция.
  Если лицензию выдать нельзя (нет мест, подписка отменена, у заявителя она
  уже есть, заявитель заблокирован), ничего не меняется: ответ 409 (или
  400), заявка остаётся в `pending_admin`.
- Решение по уже решённой или отменённой заявке — 409; два одновременных
  одобрения не выдадут двух лицензий.

```sh
# сотрудник
curl -s localhost:8080/api/v1/requests -H "Authorization: Bearer $EMP" \
  -d '{"name":"Figma","justification":"Макеты нового интерфейса","estimated_cost":1500}'
# начальник отдела
curl -s localhost:8080/api/v1/requests/1/approve -H "Authorization: Bearer $HEAD" -d '{}'
# админ: новая подписка на 5 мест
curl -s localhost:8080/api/v1/requests/1/approve -H "Authorization: Bearer $TOKEN" -d '{
  "subscription": {"type":"group","seats_total":5,"cost":"7500.00","currency":"RUB",
                   "billing_period":"month","start_date":"2026-11-01"}}'
```

## Уведомления

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| GET | `/api/v1/notifications` | все | свои уведомления, новые сверху; `?unread=true` — только непрочитанные; в ответе `unread` — сколько непрочитанных всего |
| POST | `/api/v1/notifications/{id}/read` | все | отметить прочитанным |
| POST | `/api/v1/notifications/read-all` | все | отметить все прочитанными |

Кто что получает по заявкам:

- начальник отдела — когда к нему пришла заявка (`request_created`);
- все активные админы — когда заявка дошла до них (`request_created`);
- заявитель — на каждое решение: начальник одобрил (`request_approved`,
  «передана администратору»), окончательно одобрено (`request_approved`,
  с названием выданной лицензии), отклонено (`request_rejected`, с
  комментарием).

Уведомления сохраняются в той же транзакции, что и решение: если решение не
прошло, уведомления тоже нет. Уведомления об окончании подписок и платежах
присылает шедулер (см. ниже).

## Шедулер и правила уведомлений

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| GET | `/api/v1/settings/notifications` | админ | текущие правила |
| PUT | `/api/v1/settings/notifications` | админ | `{"expiring_days":7,"payment_days":3}`, оба поля обязательны, 0…365 |

- `expiring_days` (по умолчанию 7) — за сколько дней до `end_date`
  предупреждать об окончании подписки; 0 — только в сам день.
- `payment_days` (по умолчанию 3) — за сколько дней до `next_payment_date`
  напоминать о платеже.

Изменение правил пишется в аудит (`settings.update`). Шедулер читает их в
начале каждого прогона, перезапуск не нужен.

Шедулер работает внутри сервера: первый прогон — сразу при старте, дальше
каждые `SCHEDULER_INTERVAL` (по умолчанию `1h`). «Сегодня» считается по
календарю пояса `SCHEDULER_TZ` (по умолчанию `Europe/Moscow`). Каждый прогон:

| Условие | Что делает | Кому уведомление |
|---|---|---|
| `active`, `end_date` в пределах `expiring_days` (сегодня включительно) | статус `expiring_soon` | держателям активных лицензий и всем активным админам (`subscription_expiring`) |
| `active` / `expiring_soon`, `end_date` уже прошёл | статус `expired` | всем активным админам (`subscription_expired`) |
| наступил `next_payment_date` (и он не позже `end_date`) | создаёт платёж `pending`, сдвигает `next_payment_date` на период | — |
| `next_payment_date` в пределах `payment_days` (не раньше сегодня и не позже `end_date`) | — | всем активным админам (`payment_due`) |
| `expiring_soon`, но `end_date` сдвинули дальше окна или убрали | статус обратно `active` | — |

- Отменённые (`cancelled`), истёкшие (`expired`) и удалённые подписки не
  трогаются; истёкшей о платеже не напоминаем.
- `end_date` — последний день действия: подписка до 30.10 истекает 31.10.
- Каждое событие уведомляется **один раз**: перед отправкой ключ события
  (`sub_5_expiring_2026-10-30`, `sub_5_expired_…`, `sub_5_payment_…`)
  записывается в `notification_log`, и если ключ там уже был, уведомление
  не уходит. Ключ привязан к дате события, поэтому повторные прогоны и
  перезапуски сервера дублей не дают, а сдвиг даты — это новое событие.
- Админ, у которого есть лицензия, получает одну копию, а не две.
  Заблокированные пользователи уведомлений не получают.
- Каждая подписка обрабатывается в своей транзакции с блокировкой строки:
  ключ, смена статуса, аудит и уведомления либо все сохраняются, либо нет.
  Ошибка на одной подписке не мешает остальным, следующий прогон повторит.
- Изменения шедулера пишутся в аудит с `actor_id = null` и `"by":
  "scheduler"` в `details`: `subscription.update` (новый статус или
  `next_payment_date`), `transaction.create` (платёж `pending`).
- Ручного запуска нет: чтобы проверить, поставьте подписке `end_date` на
  ближайшие дни и перезапустите сервер (или уменьшите `SCHEDULER_INTERVAL`).

## Платежи (транзакции)

Только админ.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/transactions` | список по дате платежа, новые сверху; фильтры `status`, `subscription_id`, `from`, `to` (`YYYY-MM-DD`, включительно); `order=asc` — старые сверху. Ожидаемые платежи: `?status=pending&order=asc` |
| GET | `/api/v1/transactions/{id}` | один платёж |
| POST | `/api/v1/transactions` | внести платёж вручную: `subscription_id`, `amount`, `payment_date`, необязательно `currency` (по умолчанию валюта подписки), `payment_method`, `invoice_number`; сразу `paid` |
| POST | `/api/v1/transactions/{id}/pay` | отметить оплаченным; тело необязательно: `payment_method`, `invoice_number` |
| POST | `/api/v1/transactions/{id}/fail` | отметить неуспешным |

- **Откуда берутся.** Шедулер в день `next_payment_date` создаёт платёж
  `pending` на сумму и в валюте подписки на этот момент и сразу сдвигает
  `next_payment_date` на период (+1 месяц / +3 месяца / +1 год; если дня нет
  в месяце — последний день: 31.01 → 28.02 → 28.03). Если сервер был
  выключен и дат прошло несколько — создаётся по платежу на каждую (не
  больше 24 за прогон, остальные — в следующих). Для отменённых, истёкших,
  удалённых подписок и для дат после `end_date` платежи не создаются.
  Вручную админ вносит разовые и прошлые платежи.
- **Статусы:** `pending → paid | failed`, `failed → paid`; `paid`
  окончательный (иначе 409). Повторная оплата после `failed` — та же запись.
- У подписки максимум один платёж на дату (409 при ручном вводе). Если админ
  уже внёс платёж на дату, шедулер её пропускает.
- Сумму платежа изменить нельзя.
- Все изменения пишутся в аудит: `transaction.create`, `transaction.pay`,
  `transaction.fail`.

## Аналитика

Все суммы — в рублях по текущему курсу (`amount * rate_to_rub`), строкой с
двумя знаками. «Активные» подписки — `active` и `expiring_soon`; месячная
стоимость — цена периода, делённая на его длину (1, 3 или 12 месяцев).
«Сегодня» и «этот месяц» — по поясу `SCHEDULER_TZ`.

| Путь (`GET /api/v1/analytics/…`) | Доступ | Что возвращает |
|---|---|---|
| `summary` | админ, начальник | число активных / истекающих / истёкших, месячная и годовая стоимость, места (всего, занято, свободно, % занятости), безлимитные подписки, выданные лицензии, активные пользователи, стоимость на человека в месяц. Админу ещё `payments` (оплачено в этом месяце и году, ожидает оплаты — число и сумма, просрочено, неуспешных) и `recommendations` + `potential_savings_rub` |
| `by-category` | админ, начальник | месячная стоимость по категориям (без учёта регистра), доля в % |
| `by-vendor` | админ, начальник | то же по вендорам |
| `forecast?months=12` | админ, начальник | прогноз по месяцам с текущего (до 36): платежи по графику (`next_payment_date` + период, до `end_date`), оценка для подписок без даты платежа, итог и `run_rate_rub` — сколько вышло бы, если всё продлевать |
| `by-department` | админ | все отделы: подписки, стоимость, места, люди, стоимость на человека; строка `department_id: null` — общие подписки |
| `top-subscriptions?limit=10` | админ | самые дорогие подписки: месячная и годовая стоимость, занятость, стоимость одной лицензии |
| `spending?from=2025-11&to=2026-10` | админ | реально оплачено по месяцам (по дате платежа, только `paid`), по умолчанию последние 12 месяцев, максимум 60 |
| `recommendations` | админ | советы по экономии (ниже) |

- У админа во всех отчётах, кроме `by-department`, есть `?department_id=` —
  отчёт по одному отделу.
- Начальник получает только обобщённые цифры **своего** отдела:
  `department_id` для него игнорируется, данных о платежах и рекомендаций
  нет. Начальник без отдела и сотрудник получают 403.

### Рекомендации

| Тип | Когда | Экономия в год |
|---|---|---|
| `unused_seats` | групповая подписка занята меньше чем на 80% | стоимость свободных мест: «Сократите 20 мест — сэкономите 120 000 ₽/год» |
| `no_holders` | ни одной лицензии, подписке больше 30 дней | вся годовая стоимость |
| `duplicate_vendor` | у одного вендора 2+ активных подписки на разные продукты | — |
| `individual_to_group` | 3+ индивидуальных подписки на один продукт | — |
| `enterprise_low_usage` | безлимитной подпиской пользуются меньше 10 человек | — |
| `annual_billing` | помесячная оплата дольше 12 месяцев | — |
| `expired_with_holders` | подписка истекла, а лицензии остались | — |

Сортировка — по экономии, советы без рассчитанной экономии
(`savings_rub_year: null`) идут после. Экономию считаем только там, где она
следует из данных системы; где нужна чужая цена (годовой тариф, групповая
подписка), её нет.

## Аудит

`GET /api/v1/audit` — только админ. Кто, что и когда изменил, новые сверху.
Фильтры: `actor_id`, `entity_type` (`user`, `department`, `subscription`,
`assignment`, `request`, `settings`, `transaction`), `entity_id`, `action`, `from`, `to` (даты
`YYYY-MM-DD`, включительно).

- Пишется каждое изменение: пользователи (создание, правка, блокировка,
  сброс и смена пароля), отделы, подписки (в том числе отмена и удаление —
  с числом отозванных лицензий), выдача и отзыв лицензий, заявки (подача,
  решения, отмена). Чтение не пишется, отметка «прочитано» тоже.
- `action` — `<сущность>.<глагол>`, например `assignment.revoke`,
  `request.approve`. В `details` — что изменилось (новые значения полей);
  паролей и их хэшей там нет.
- `actor_id = null` — действие системы: создание первого админа и
  изменения шедулера — статусы подписок, даты платежей, платежи `pending`
  (`details.by = "scheduler"`).
- Запись аудита делается в той же транзакции, что и изменение: изменения без
  записи в журнале не бывает.

## Деньги и валюты

Каждая сумма хранится как `NUMERIC(14,2)` вместе с кодом валюты из таблицы
`currencies`. У каждой валюты есть курс к рублю (`rate_to_rub`), который
админ задаёт вручную; у рубля курс всегда 1. Отчёты и аналитика переводят всё
в рубли по **текущему** курсу: `amount * rate_to_rub`. Историю курсов система
не хранит, это сознательное упрощение.

## Разработка

```sh
make test    # go test ./...
make vet     # go vet ./...
make build   # бинарник в bin/subtrack
make swagger # пересобрать docs/ после изменения маршрутов или DTO
```

Swagger строится из аннотаций: общая информация — над `main()` в
`cmd/server/main.go`, у каждого обработчика — свой godoc-блок
(`@Summary`, `@Param`, `@Success`, `@Router`…). Тест
`TestSpecMatchesRouter` (internal/server) падает, если `docs/swagger.json`
не совпадает с реальными маршрутами, — значит, забыли `make swagger`.
